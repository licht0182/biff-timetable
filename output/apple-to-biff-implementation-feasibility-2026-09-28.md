# Apple 홈페이지 UI/UX를 BIFF Timetable에 적용할 수 있는가

**대상:** [Apple 대한민국 홈페이지 분석 보고서](apple-kr-ui-ux-report-2026-09-28.md)와 현재 `biff-timetable` 작업 디렉터리
**조사일:** 2026년 9월 28일
**방법:** 현재 소스·데이터 구조를 읽고, 로컬 개발 화면을 Chromium에서 1440×900px 및 390×844px로 직접 확인했다. 이 보고서는 **구현 가능성 분석**이다. 앱 소스는 수정하지 않았다. 현재 작업 디렉터리에 이미 미커밋 변경이 있으므로 판단은 해당 시점의 작업 트리 기준이다.

## 1. 결론

**기술적으로는 구현할 수 있다.** React 19·Vite 7·TypeScript·CSS로 Apple 홈페이지의 전폭 히어로, 반응형 이미지, 메뉴 오버레이, 프로모션 그리드, 갤러리, 타이포그래피 위계를 재현할 수 있다. 그러나 **Apple 사이트와 픽셀까지 동일한 BIFF 사이트**는 현재 앱에 CSS만 덧씌워 완성되는 작업이 아니다. 화면 구조와 콘텐츠 파이프라인을 새로 만들고, BIFF의 검색·상영 선택·시간표 사용성을 재설계해야 한다.

| 목표 해석 | 판정 | 이유 |
|---|---|---|
| Apple의 정보 위계·여백·큰 이미지·명확한 CTA를 BIFF 브랜드로 적용 | **가능, 권장** | 공통 UI 원리는 옮길 수 있고 기존 영화 탐색·시간표 기능을 유지할 수 있다. |
| BIFF 첫 화면을 Apple식 캠페인 랜딩으로 구성 | **가능, 조건부** | 사진 선별, 홈 화면 컴포넌트, 반응형 자산, 검색 진입점 재배치가 필요하다. |
| 모든 화면을 Apple 홈페이지와 똑같이 보이게 변경 | **기술적으로 가능하지만 부적합** | 제품 판매용 전시 페이지와 270편을 검색·선택하는 도구는 정보 밀도와 조작 목적이 다르다. Apple의 고유 웹 디자인·로고·이미지·서체를 모방하거나 재사용하는 문제도 있다. |

Apple의 [상표·저작권 사용 지침](https://www.apple.com/legal/intellectual-property/guidelinesfor3rdparties.html)은 제삼자가 Apple의 독특한 웹사이트 디자인과 로고·서체를 모방하는 일을 금지한다고 명시한다. [웹사이트 이용 약관](https://www.apple.com/legal/internet-services/terms/site.html)도 사이트의 구성·표현·외관과 콘텐츠를 보호 대상으로 설명한다. 따라서 구현 방향은 **Apple의 일반적인 UX 원리를 연구해 BIFF 고유 디자인으로 재구성**하는 것이다. 이는 기술·제품 분석이며 개별 이용 허가에 대한 법률 판단은 아니다.

## 2. 현재 BIFF 앱의 실제 구조

### 소스와 런타임

- `src/App.tsx` 약 **1,587행**이 영화 검색, 상세, 선택, 시간표 목록·그리드, 예매 우선순위, 사용자 일정, 설정, 모달의 상태와 화면 분기를 조합한다. 기본 탭은 영화 찾기다.
- `src/main.tsx`는 현재 **20개 CSS 파일**을 순서대로 불러온다. 뒤쪽의 `src/liquid-glass.css`, `src/layout-system.css`, `src/text-chip.css`가 앞의 구식 규칙을 덮는 구조이므로 전역 색·반경 변경은 영향 범위가 넓다.
- `src/layout-system.css`는 최대 **1180px** 앱 셸과 `700px` 이하 모바일 레이아웃을 제어한다. `src/liquid-glass.css`는 반투명 소재·색·다크 모드·움직임/투명도 감소 대응을 담당한다.
- 데스크톱에는 상단 `.topbar`와 `.tabs`, 모바일에는 고정된 `LiquidTabBar`의 **영화 찾기·내 시간표·AI 도슨트·설정** 네 항목이 있다.
- `src/components/FilmList.tsx`는 `react-virtuoso`로 영화 목록을 가상화한다. `public/screenings.json`의 현재 영화 목록은 **270개 항목**이다.
- `src/navigation-history.ts`는 탭·설정·도슨트 글을 History state에 저장하되 URL 경로 자체는 바꾸지 않는다. Apple처럼 카테고리마다 별도 주소를 쓰는 구조와 다르다.
- `vite.config.ts`는 `/biff-timetable/` 하위 경로의 PWA, 독립 실행 모드, 서비스 워커 탐색 대체 경로를 설정한다. `src/film-data.ts`는 상영 데이터 네트워크 로드와 `localStorage` 캐시를 처리한다.

| 표본 | Apple 홈페이지 | 현재 BIFF Timetable |

| 390px 첫 화면 | 500px 제품 히어로가 화면 대부분을 차지 | 검색 입력이 상단 약 **183px**부터 시작하고 첫 영화 카드가 약 **425px**에서 시작 |
| 메뉴 | 834px 이상 고정 전역 헤더·메가 메뉴, 그 아래 모바일 전체 화면 단계형 메뉴 | 700px 초과 상단 탭, 700px 이하 하단 4항목 도크 |

## 4. 이미지·콘텐츠가 가장 큰 선행 조건

현재 화면이 사용하는 `public/screenings.json`의 `Film` 타입(`src/components/film-types.ts`)에는 포스터·스틸 이미지 필드가 없다. 반면 별도 `public/films-2026.json`에는 **246개 상세 레코드**와 사진 정보가 있다. 상영작의 공식 URL에 포함된 `idx`를 상세 데이터의 `biff.idx`와 직접 맞춰 보니 **270개 중 219개**를 연결할 수 있었다. 나머지 **51개**는 개·폐막 행사, 단편 묶음, 클래스 등의 복합·행사 항목이 포함돼 직접 연결되지 않았다.

연결 가능한 219개 상세 레코드는 모두 하나 이상의 영화 사진을 갖는다. 총 **919개 `filmPhoto` 항목**이 있으나 해당 사진 항목의 `alt`는 모두 빈 문자열이었다. 일부 사진에는 개별 크레딧/캡션이 있고, 상세 레코드에는 저작권 고지 목록이 있다. 이 상태로 Apple처럼 이미지 중심의 큰 타일을 만들려면 다음이 필요하다.

1. **콘텐츠 매핑:** `idx`를 기준으로 영화 사진을 선택하고, 복합 상영·행사 51개에는 별도 대표 이미지 또는 브랜드 그래픽 폴백을 지정한다.
2. **편집:** 상영작마다 이미지가 여러 장 있으므로 대표 사진, 모바일 세로 크롭, 데스크톱 가로 크롭, 한 줄 제목과 CTA를 선택한다. 원본 해상도와 실제 크롭 품질은 별도로 검수해야 한다.
3. **접근성:** 빈 `alt`를 그대로 쓰지 말고 정보 전달 이미지에는 장면 설명을 작성한다. 장식 배경으로 쓰는 경우에는 적절한 빈 `alt`와 별도 텍스트 제목을 둔다.
4. **권리·성능:** BIFF 데이터의 저작권 고지를 이미지의 배포 허가로 간주할 수 없다. 사용 범위를 확인하고, 최적화된 크기·형식·지연 로딩·캐시 정책을 설계한다. Apple의 이미지를 가져다 쓰는 방식은 제안하지 않는다.

즉 **디자인 코드보다 사진 선별·사용 가능 여부·구도 제작이 시각적 유사도를 좌우**한다.

## 5. 소스 변경 지점과 설계 방향

| 작업 영역 | 변경 예상 위치 | 권장 방식 | 주의점 |
|---|---|---|---|
| 홈/편집 페이지 | 새 컴포넌트, `src/App.tsx`의 탭 상태 | 기존 영화 찾기와 분리된 BIFF 소개/추천 면을 추가하거나 AI 도슨트 첫 영역을 확장 | 기본 진입 경로를 바꾸면 검색 전환이 느려짐 |
| 공통 셸·타이포그래피 | `src/layout-system.css`, `src/liquid-glass.css`, `src/main.tsx` | 여백·폰트 규모·CTA·색 토큰을 먼저 정리하고 화면별로 적용 | 20개 CSS의 우선순위·후행 오버라이드 확인 필요 |
| 데스크톱 탐색 | `src/App.tsx` 상단 `.topbar`/`.tabs` | BIFF 네 영역과 정보 페이지를 위한 간결한 메뉴 | Apple의 11개 카테고리를 그대로 만들 이유가 없음 |
| 모바일 탐색 | `src/components/LiquidTabBar.tsx`, 관련 CSS | 현재 고정 도크와 선택 상태 유지; 보조 메뉴만 새 패턴 | iPhone 안전 영역·WebKit 합성·모달과 도크 충돌 검증 |
| 영화 검색·상세 | `FilmSearchAutocomplete.tsx`, `FilmCard.tsx`, `ScreeningRow.tsx` | 상단 이미지/제목을 정돈하되 필터·회차·선택 버튼은 즉시 접근 가능하게 | 큰 이미지가 카드 높이와 가상 목록 스크롤 비용을 늘림 |
| 시간표 | `ScheduleList.tsx`, `src/App.tsx` 그리드, `src/timetable-*.css` | Apple식 여백·위계 중 적합한 부분만 적용 | 분 단위 위치, 충돌 표시, 우선순위, 밀집 화면을 반드시 보존 |
| 도슨트·갤러리 | `CuratorPage.tsx`, `src/curator.css` | 편집형 영웅 영역·추천 카드·선택형 갤러리의 우선 후보 | 정지 버튼, 키보드 탐색, 축소 동작 설정 필요 |
| 데이터·PWA | `film-types.ts`, `film-data.ts`, `vite.config.ts`, `navigation-history.ts` | 이미지 메타데이터·경로·캐시 정책을 명시적으로 확장 | 기존 저장 데이터, 오프라인 상태, 하위 경로 `/biff-timetable/` 호환 |

**구현 순서 제안:** 새 화면을 곧바로 전체 앱에 덮지 않고, 먼저 BIFF 고유 색·타이포·버튼 규칙을 정의한 뒤 도슨트/편집 면에서 히어로와 프로모션을 검증한다. 이후 검색 카드와 시간표에 필요한 부분만 옮긴다. 이 순서가 이미지 중심의 홍보 UI와 데이터 중심의 도구 UI를 각자 목적에 맞게 조정하기 쉽다.

## 6. 난이도와 대략적인 범위

아래는 **현재 코드를 아는 개발자 1명**, BIFF 사진 사용 가능 여부가 확인되고 카피·대표 이미지가 제공된다는 가정의 개발·QA 추정이다. 디자인 자산 제작·권리 검토·새 콘텐츠 편집 시간은 제외한다.

| 범위 | 대략적 개발 범위 | 포함 내용 |
|---|---:|---|
| Apple의 정보 위계만 BIFF 현재 화면에 반영 | **5–10 개발일** | 제목·여백·CTA·카드 위계, 핵심 반응형 점검 |
| BIFF 브랜드의 Apple식 편집 랜딩 추가 | **10–20 개발일** | 히어로·프로모션·이미지 매핑·메뉴/검색 진입·모바일 및 WebKit QA |
| 네 탭 전체를 하나의 새 디자인 시스템으로 재구성 | **20–35 개발일 이상** | 기존 20개 CSS 정리, 영화·시간표·도슨트·설정 및 모든 대화상자·PWA 회귀 검증 |
| Apple 페이지와 픽셀 단위 동일한 복제품 | **권장 범위로 산정하지 않음** | Apple 고유 자산·웹 디자인 사용 조건과 BIFF 콘텐츠 목적이 해결되지 않음 |

기간은 구현 난이도의 상대적 크기를 보여 주는 초안이다. 선택할 화면 범위, 사진 제공 방식, 디자인 시안, 접근성 기준이 정해지면 다시 산정해야 한다.

## 7. 구현한다면 반드시 확인할 수용 기준

1. **기능 보존:** 영화 270개 검색·필터, 회차 선택, 시간 충돌, 예매 상태·우선순위, 사용자 일정, 백업·복원, 설정을 그대로 사용할 수 있다.
2. **첫 화면 작업성:** 390px에서 검색 또는 영화 찾기 행동이 즉시 보이고 하단 도크와 겹치지 않는다. 히어로를 추가해도 사용자가 첫 행동을 이해한다.
3. **반응형:** 320·390·700·768·1024·1440px에서 가로 넘침, 긴 제목 잘림, 사진 속 피사체 손실, 버튼 겹침을 확인한다. Apple의 734/833/1068px 경계를 BIFF에 그대로 강제하지 않는다.
4. **접근성:** 메뉴/갤러리의 포커스 이동과 Escape, 이미지 대체 텍스트, 충분한 대비, 키보드 회차 선택, 움직임·투명도 감소 설정을 검증한다.
5. **기기 동작:** Chromium과 iPhone WebKit의 일반 사이트에서 안전 영역, 다크 모드, 하단 도크, 스크롤·모달 전환을 확인한다. 2026년 9월 30일 사용자가 iPhone 17 실기기 확인 전 항목 통과를 회신했다. 이후 사용자 지시에 따라 별도 PWA 검사를 하지 않고 일반 사이트 통과를 PWA 통과로 판정한다.
6. **성능·데이터:** 사진 로딩이 가상 목록의 스크롤 성능과 첫 화면 표시를 해치지 않고, 사진이 없거나 오프라인이어도 영화 정보·시간표가 계속 동작한다.

현재 로컬 개발 화면의 주요 세 탭은 실제 브라우저에서 열어 확인했다. **이 보고서는 소스 수정·빌드·전체 E2E를 수행한 결과가 아니므로 구현 완료 판정은 아니다.**
