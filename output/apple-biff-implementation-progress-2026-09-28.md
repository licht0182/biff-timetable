# Apple 홈페이지 분석 기반 BIFF Timetable 구현 진행 현황

작성일: 2026-09-28
기준 문서: [Apple 한국 홈페이지 UI/UX 분석](apple-kr-ui-ux-report-2026-09-28.md), [BIFF 적용 가능성 분석](apple-to-biff-implementation-feasibility-2026-09-28.md)

## 적용 범위와 판단

Apple 홈페이지에서 관찰한 큰 제목, 콘텐츠별 시각적 위계, 넓은 이미지 면, 짧고 명확한 행동 버튼, 반응형 카드 배치를 **BIFF 고유 콘텐츠와 빨강 브랜드**에 맞춰 적용했다. 영화 찾기를 기본 진입 화면으로 유지하고 AI 도슨트 목록을 편집형 화면의 첫 실험 영역으로 삼았다. 영화·시간표의 데이터 중심 기능이나 하단 도크의 정보 구조는 바꾸지 않았다. Apple의 로고·폰트·이미지·문구·픽셀 단위 레이아웃은 복제하지 않았다.

## 확인 결과

- 1차 시점에 `npm run build`, `npm run validate:curator`, `git diff --check` 통과. 당시 남아 있던 PWA `theme_color` 경고는 아래 2차에서 해소했다.
- 실제 Chromium 화면에서 320·390·700·768·1024·1440px 가로 넘침 없음. 모바일 영화 검색 입력 상단은 320px에서 약 183px, 390px에서 약 152px로 첫 화면에 남는다.
- 390px AI 도슨트 사진 3장이 로드되고 `alt`·출처가 표시된다. 대표 CTA→상세→브라우저 뒤로 가기 경로 확인.
- WebKit iPhone 레이아웃·모바일 탐색 관련 20개 테스트 통과. 도슨트 모듈 준비 시점을 조정한 뒤 관련 Chromium/WebKit 회귀 세트 65개가 통과했고, 최종 CI 조건의 전체 Chromium/WebKit E2E **189개 모두 통과**(`CI=1 npm run test:e2e -- --reporter=line`). 그 전 병렬 실행에서는 도슨트의 동적 로딩 대기 실패가 있었고 단독 반복 3회는 통과했다. 최종 세트에는 사진 요청 실패 시 대체 표시·출처·칼럼 이동·뒤로 가기 검사 1개가 추가되었다.
- 다크 모드 대표 CTA의 흰 글자 대비는 BIFF 빨강 배경에서 약 5.63:1이다. 새 편집 섹션 라벨은 약 8.11:1, 카드 분류 배지는 합성 배경 기준 약 5.79:1이며, 미선택 회차 버튼은 어두운 화면용 밝은 빨강을 사용한다.

## 남은 확인 사항

원격 영화 사진은 공식 데이터의 URL과 저작권 표기를 사용하지만, BIFF 외 앱에서의 재사용 허가는 별도 확인이 필요하다. 사진이 끊기면 내용 중심 폴백이 표시된다. 도슨트 청크는 gzip 약 126KB이며 첫 렌더 600ms 뒤 미리 읽는다. 병렬 WebKit 탐색의 로딩 안정성은 개선되었지만 저속망에서 영화 검색 데이터와 경합하는지 배포 후 측정해야 한다. 1차 구현은 네 탭 전체의 시각 체계 통합이나 시간표 재설계를 포함하지 않았다.

## 2차 구현: 공통 셸·검색·사진 검증

| 영역 | 적용 내용 |
|---|---|
| 공통 시각 체계 | `src/biff-design-tokens.css`를 마지막에 불러와 네 탭의 셸·상단 메뉴·주요 버튼에 BIFF 색상, 간격, 글자 위계를 적용했다. 기존 시간표의 밀집 정보와 네 탭 구조는 유지했다. |
| 전체 검색 | 상단의 `전체 검색` 버튼과 접근 가능한 모달을 추가했다. 영화 검색, 상세 필터, 영화 찾기·시간표·AI 도슨트·설정 바로가기를 제공하고, Escape 종료·초점 복원·이동 후 초점 위치를 검사한다. |
| 사진·PWA | 대표 사진은 우선 로드하고 후속 사진은 지연 로드한다. `validate:curator-media`가 공식 데이터 연결, 대체 텍스트, 출처, 중복을 검증하며 CI·배포 빌드에서도 실행된다. 밝은/어두운 화면의 브라우저 테마 색과 매니페스트 배경색을 BIFF 셸에 맞췄다. |

`npm run validate:data`, `validate:films`, `validate:curator`, `validate:curator-media`, `npm run build`, `git diff --check`가 통과했다. 2차 변경에 대한 Chromium·iPhone WebKit 전체 E2E는 222개가 통과했다. 그 뒤 검색 모달의 이동 후 초점을 고쳤고, 다시 빌드한 결과로 전체 검색 E2E 8개가 통과했다.

## 3차 구현: 도슨트 갤러리·정보 푸터

AI 도슨트의 대표·프로모션에 쓰지 않은 감독 가이드 5개를 `CuratorGallery.tsx`에 연결했다. 갤러리는 처음에 정지해 있고 사용자가 요청한 경우에만 6초 간격으로 넘긴다. 이전·다음, 번호 선택, 갤러리 탐색 영역에 초점을 둔 상태의 방향키·Home·End, 가로 스와이프를 지원한다. 칼럼·영화 버튼에 초점이 있을 때에는 갤러리 단축키가 개입하지 않는다. 포커스·마우스 진입·백그라운드 전환은 자동 넘김을 중지하고, 움직임 줄이기 설정에서는 자동 넘김을 사용할 수 없다. 현재 사진만 렌더링하며 지연 로드한다. 사진 오류 시 작품명과 재시도 버튼을 표시하고 온라인 복귀 시 자동 재시도한다. 출처·칼럼·영화 찾기 링크는 유지한다. 2026-09-28 `HEAD` 응답 기준 추가한 사진은 각각 약 183–414KB, 다섯 장 합계 약 1.44MB이므로 전체를 한꺼번에 요청하지 않도록 했다.

앱 하단에는 공식 시간표·2026 작품 정보 링크와 비공식 도구 안내를 담은 푸터를 추가했다. 영화 찾기·시간표의 첫 화면 위쪽에는 놓지 않았고, 390px에서 하단 도크와 겹치지 않음을 확인했다. 두 공식 링크는 2026-09-28에 HTTP 200으로 확인했다.

`npm run build`가 통과했다. 실제 Chromium·iPhone WebKit에서 320·390·700·768·1024·1440px 갤러리의 가로 넘침이 0px이었고, 390px·1440px 화면을 육안 확인했다. 전체 E2E 첫 실행은 234건 중 224건이 통과했고, 나머지 10건은 새 갤러리 번호 버튼과 기존 칼럼 카드가 같은 접근성 이름을 갖게 된 테스트 선택자 충돌이었다. 칼럼 카드로 선택자를 좁힌 후 도슨트 스펙 52건과 갤러리 다크 모드 2건이 통과했다. 이어서 독립 리뷰에서 발견한 키보드 조작 범위와 사진 복구 문제를 수정한 뒤 빌드와 Chromium·iPhone WebKit 갤러리 집중 검사 10건, 푸터·오프라인 검사 3건이 통과했다. Chromium 설치형 PWA에서는 네트워크를 끊고 새로 열어도 영화 목록·도슨트 텍스트가 표시되고 원격 사진은 대체 표시로 전환되는 것을 확인했다. 스와이프 테스트는 합성 터치 이벤트를 사용했으므로 실제 손가락 동작은 실기기 확인이 필요하다.

화면 증거: [iPhone WebKit 390px](apple-biff-gallery-webkit-iphone-390.png), [Chromium 1440px](apple-biff-gallery-chromium-1440.png).

## 4차 구현: 저속망에서 영화 목록 우선 로드

도슨트 코드를 첫 화면에서 600ms 후 읽던 방식을 바꿨다. 영화 데이터가 화면에 준비된 뒤 600ms가 지나야 미리 읽고, 브라우저가 `3g`·`2g`·`slow-2g` 또는 데이터 절약 모드를 보고하면 자동 미리 읽기를 생략한다. 사용자가 AI 도슨트를 열면 연결 상태와 관계없이 정상 로드한다. 연결 정보 API가 없는 WebKit에서도 영화 목록이 준비되기 전에는 미리 읽지 않는다.

2026-09-29 로컬 Chromium에서 서비스 워커를 끄고 RTT 300ms·다운로드 80KiB/s로 제한해 두 번씩 측정했다. 변경 전 첫 영화 카드 표시가 7,279ms·7,164ms였고, `screenings.json` 약 167KB와 도슨트 코드 약 128KB의 전송이 겹쳤다. 변경 후 5,668ms·5,629ms였으며, 관측 구간에서 도슨트 코드 요청은 발생하지 않았다. 이는 이 테스트 환경의 소수 표본이며 실제 이동통신망·iPhone의 성능 수치로 일반화할 수 없다. 새 요청 정책을 Chromium·WebKit E2E 2건과 빌드로 확인했다.

## 5차 구현: 시간표 목록의 정보 위계와 다크 모드 가독성

실제 2026-10-11 상영 일정 6개와 겹치는 시간대 2개를 넣어 목록을 확인했다. 어두운 화면에서 날짜 제목과 시작 시간이 거의 검정색으로 표시되고, 상영관·종료 예상 시간·충돌 안내도 읽기 어려웠다. `schedule-list.css`의 고정 색을 BIFF 글자 토큰으로 바꾸고 날짜 수량·시간·상영관·충돌 안내의 작은 글자를 조정했다. 시간표 도구 모음의 선택 수량과 이동시간 안내도 같은 보조 글자색을 사용한다. 상영 시각·그리드 위치·선택·충돌 데이터는 변경하지 않았다.

`npm run build`와 시간표 레이아웃·메뉴 E2E 34건, 새 가독성 E2E Chromium·iPhone WebKit 2건이 통과했다. 새 테스트는 어두운 화면의 날짜·시간·상영관·충돌 안내·상태 배지가 각각 배경에 대해 4.5:1 이상의 대비를 유지하는지 계산한다. 로컬 Chromium에서 320·390·700·768·1024·1440px 가로 넘침이 없었고, 390px 밝은/어두운 화면과 1440px 밝은 화면을 육안 확인했다. 화면 증거: [모바일 밝은 화면](apple-biff-timetable-light-390.png), [모바일 어두운 화면](apple-biff-timetable-dark-390.png), [데스크톱 밝은 화면](apple-biff-timetable-light-1440.png).

## 6차 구현: 영화 상세에서 회차 행동 우선

긴 작품 소개가 모바일 첫 화면을 차지해 상영 회차가 아래로 밀리는 상태를 확인했다. `FilmSynopsis.tsx`에서 긴 소개는 앞의 4줄을 먼저 보여 주고 `줄거리 더 읽기`로 전체를 펼친다. 버튼은 펼침 상태를 알리고 키보드로 작동하며, 상세를 닫았다 다시 열면 기본 상태로 돌아간다. 본문 전체와 기존 회차·예매·관심작 기능은 유지한다. 영화 제목의 위계를 높이고, 아직 선택하지 않은 회차의 `+ 추가` 버튼은 BIFF 빨강으로 구분했다. 사진 재사용 허가가 불명확한 상태에서 새 사진을 영화 상세에 추가하지 않았다.

390px 밝은/어두운 화면에서 세 회차가 첫 화면에 보이고, 320×640px에서도 첫 회차 버튼이 보이는 것을 확인했다. `npm run build`, Chromium·iPhone WebKit의 펼침·접기·회차 선택 E2E 2건, 기존 작품 소개·장르·상세 이동 검사 5건이 통과했다. 화면 증거: [320px](apple-biff-film-detail-light-320.png), [390px 밝은 화면](apple-biff-film-detail-light-390.png), [390px 어두운 화면](apple-biff-film-detail-dark-390.png), [1440px](apple-biff-film-detail-light-1440.png).

## 7차 구현: 작은 화면의 날짜별 시간표 그리드

기존 390px 화면에서 열흘의 일정이 모두 선택되면 날짜 열이 약 33px로 압축돼 작품명을 읽기 어려웠다. 1023px 이하의 시간표 그리드는 날짜 선택 줄에서 하루를 고르면 해당 날짜의 열 하나를 넓게 보여 준다. 날짜 버튼은 가로 스크롤과 좌우 방향키·Home·End 탐색을 지원하며, 선택한 날짜의 마지막 일정을 삭제하면 남은 첫 날짜로 돌아간다. 1024px 이상에서는 여러 날짜를 한눈에 보는 기존 그리드를 유지한다. 시간당 40px와 분 단위 위치, 겹침 레인, 목록 보기와 저장 형식은 유지했다.

하루 보기의 일정 제목·보조 정보 크기를 높이고, 영화·사용자 일정 버튼의 접근성 이름에 날짜, 시작·종료 시각, 장소, 예매 상태·우선순위, 충돌·이동 경고를 담았다. 날짜 선택과 키보드 초점은 밝은·어두운 화면 모두 BIFF 색 토큰을 사용하고, 날짜 버튼의 최소 높이는 44px다. `npm run build`, 새 날짜 전환·삭제·반응형 검사 Chromium·iPhone WebKit 16건과 관련 시간 범위·뷰포트·회차 표시 검사를 포함한 23건이 통과했다. 해당 커밋의 원격 전체 검증·Pages 배포 워크플로도 성공했다. 실제 브라우저에서 390px 밝은/어두운 화면, 700px 단일 날짜, 1440px 열흘 보기를 확인했다. 화면 증거: [390px 밝은 화면](apple-biff-grid-day-focus-light-390.png), [390px 어두운 화면](apple-biff-grid-day-focus-dark-390.png), [700px](apple-biff-grid-day-focus-light-700.png), [1440px](apple-biff-grid-day-focus-light-1440.png).

## 8차 구현: 설정 화면의 표와 설명 가독성

설정 화면에서 밝은 배경의 회색 설명 글자와 8–10px 표·주석이 읽기 어려운 상태를 확인했다. `settings-editorial.css`를 공통 BIFF 토큰 뒤에 적용해 설명·행·이동시간 표를 최소 12px로 높이고, 설명색을 밝은 화면 `#53565d`, 어두운 화면 `#c5c5cb`로 조정했다. 표는 화면 안에서 가로로 스크롤하며 출발 상영관 첫 열은 고정한다. 밝은 화면에서 표를 끝까지 밀었을 때 뒤 셀의 글자가 첫 열에 비치는 문제를 재현해 첫 열 배경을 불투명하게 수정했다. 표 머리글에는 `scope="row"`/`scope="col"`을 지정했고, 기본값 초기화 버튼은 최소 46px 높이다. 설정값·기본값·저장 구조는 유지했다.

`npm run build`, 새 설정 가독성·표 스크롤 검사와 기존 설정 스크롤 검사를 합친 Chromium·iPhone WebKit **24건**이 통과했다. 실제 390px 밝은·어두운 화면과 밝은 화면의 표 가로 스크롤을 확인했다. 화면 증거: [밝은 화면](apple-biff-settings-light-390.png), [어두운 화면](apple-biff-settings-dark-390.png), [고정 첫 열](apple-biff-settings-matrix-scroll-light-390.png).

## 9차 구현: 대화상자와 모바일 필터의 초점 흐름

영화 상세, 예매 충돌, 예매 대안 적용, 사용자 일정의 네 커스텀 오버레이와 모바일 상세 필터를 브라우저 기본 `<dialog>.showModal()` 계층으로 옮겼다. 배경 입력 차단과 중첩 순서를 브라우저가 처리하며, `Escape`는 맨 위 창 하나만 닫는다. 공통 초점 처리에서 열릴 때 닫기 버튼 또는 일정명 입력으로 이동하고, 첫·마지막 컨트롤의 Tab/Shift+Tab을 창 안에서 순환시킨다. iPhone WebKit에서 탭 입력이 호출 버튼에 포커스를 남기지 않는 경우도 있어 포인터·클릭·키보드 활성화 대상을 기록하고, 닫은 뒤 연결된 호출 버튼으로 복귀시킨다. 영화 상세 위의 예매 충돌창을 닫으면 회차 추가 버튼으로 돌아가고, 이어 영화 상세를 닫으면 원래 카드로 돌아간다. 사용자 일정 상세에서 수정으로 전환할 때는 같은 창 안의 일정명 입력으로 초점을 옮긴다. 데스크톱 필터는 기존 인라인 형태로 유지했다.

`npm run build`와 새 모달 초점·전체 검색·예매·사용자 일정·모바일 레이아웃 관련 Chromium·iPhone WebKit E2E **100건**이 통과했다. 390px 밝은·어두운 필터 시트와 영화 상세를 실제 브라우저에서 확인했고, 시트의 하단 고정·안전 영역·배경 흐림·닫기 버튼 한 줄 배치를 확인했다. 화면 증거: [밝은 필터 시트](apple-biff-native-filter-390-final.png), [어두운 필터 시트](apple-biff-native-filter-dark-390.png), [영화 상세](apple-biff-native-film-dialog-390.png). 설치된 iPhone PWA의 소프트 키보드와 보조 기술 동작은 실기기 검증이 남아 있다.

## 10차 구현: 데스크톱 밀집 시간표와 공식 변경 안내

열흘에 걸친 26개 일정 가운데 같은 날 세 일정이 겹치는 상태를 1024px·1440px에서 재현했다. 기존 여러 날짜 그리드는 겹침 레인이 약 30px로 좁아져 제목을 읽기 어려웠다. 데스크톱에서도 날짜·겹침 수·실제 레인 간격으로 카드 너비를 계산해 88px 미만이면 가장 밀집한 하루를 자동으로 넓게 보여 준다. 사용자는 `전체 날짜`로 전체 그리드를 다시 볼 수 있고, `하루 자세히`로 돌아올 수 있다. 선택 일정의 시간·위치·저장 데이터와 1023px 이하의 하루 보기는 유지했다. 일정 카드의 최소 높이는 22px로 통일했다. 화면 증거: [1024px 밀집 하루 보기](playwright/apple-biff-desktop-dense-focus-1024-final.png), [1440px 밀집 하루 보기](playwright/apple-biff-desktop-dense-focus-1440-final.png).

BIFF의 [공식 상영·행사 변경 안내](https://www.biff.kr/kor/artyboard/mboard.asp?Action=view&intSeq=102705&strBoardID=9611_03)에서 추가 상영·GV·프로그램 행사 변경을 확인했다. 영화 찾기의 검색·필터 아래에 해당 공지로 가는 짧은 리본을 추가했다. 공지 내용을 앱 데이터에 자동 반영하는 기능은 아니다. 390px에서도 검색 입력이 리본보다 먼저 나오며, 밝은 화면 390px·1440px에서 배너와 첫 영화 카드를 확인했다. 화면 증거: [390px 공식 안내](playwright/apple-biff-official-ribbon-390.png), [1440px 공식 안내](playwright/apple-biff-official-ribbon-1440.png).

`npm run build`와 날짜 집중 보기·공식 안내·모바일 레이아웃·레이아웃 간격 검사를 합친 Chromium·iPhone WebKit E2E **78건**이 통과했다. 이 검사는 로컬 브라우저 결과이며 설치된 iPhone PWA의 실제 동작을 대체하지 않는다.

## 11차 구현: 빈 시간표의 주 행동과 작은 화면 터치 영역

빈 시간표에서 모바일 행동 버튼이 한 줄에서 불규칙하게 줄바꿈되고 `더보기`의 터치 높이가 36px인 상태를 확인했다. 700px 이하에서는 보기 방식 두 버튼, `영화 찾기`·`일정 추가`, 백업 메뉴를 차례로 배치하고 공통 텍스트 칩의 높이 하한을 이 영역에서 44px로 지정했다. `영화 찾기`는 BIFF 빨강 주 행동으로 구분하고, 선택된 보기 방식의 파란 상태색과 701px 이상 가로 배치는 유지했다. 일정 데이터·백업 동작은 변경하지 않았다.

`npm run build`와 시간표 메뉴·레이아웃·모바일 회귀 검사 Chromium·iPhone WebKit **52건**이 통과했다. 실제 브라우저에서 320·390·700·1440px 가로 넘침이 없고, 390px 밝은·어두운 화면의 버튼과 하단 도크가 겹치지 않음을 확인했다. 화면 증거: [320px](playwright/apple-biff-empty-timetable-320.png), [390px 밝은 화면](playwright/apple-biff-empty-timetable-390.png), [390px 어두운 화면](playwright/apple-biff-empty-timetable-dark-390.png), [1440px](playwright/apple-biff-empty-timetable-1440.png).

## 12차 구현: 느린 네트워크의 저장 데이터 우선 표시와 자동 캐시 버전

기존 앱은 같은 빌드의 유효한 상영 데이터가 브라우저에 저장돼 있어도 `screenings.json` 응답이 끝날 때까지 영화 목록을 보여 주지 않았다. 이제 저장 데이터를 즉시 표시하고 최신 응답을 뒤에서 확인한다. 확인 중에는 저장 시각과 갱신 상태를 알리며, 응답이 오면 최신 데이터로 교체한다. 요청이 실패하면 저장 데이터와 다시 확인 버튼을 유지한다. 상태 안내는 영화 찾기와 내 시간표 양쪽에서 보인다.

상영 데이터 버전 문자열도 수동 날짜 대신 빌드 시 `public/screenings.json` 내용의 SHA-256 해시에서 생성한다. 데이터가 바뀐 빌드는 이전 캐시를 사용하지 않으며 요청 URL도 새 버전을 사용한다. `npm run build`와 Chromium·iPhone WebKit의 데이터 신뢰성·접근성 E2E **18건**, Chromium 설치형 PWA 오프라인 E2E **1건**이 통과했다. 병렬 첫 실행에서는 기존 PWA 검사의 서비스 워커 제어 대기가 한 번 시간 초과됐으나, 단독 재실행은 통과했다. 실제 iPhone 설치형 PWA 검증은 여전히 남아 있다.

## 13차 구현: 9월 29일 공식 상영 일정 갱신

BIFF 공식 작품·날짜별 상영표를 다시 수집해 작품 상세 **247편**, 앱의 영화·행사 항목 **273개**, 상영·행사 회차 **752개**를 반영했다. 직전 데이터의 749개 회차 ID는 유지하고 743번 《그래비티》, 815번 마스터 클래스, 827번 씨네 클래스를 추가했다. 806번 행사 시작 시각, 065·742번 GV 여부와 변경 공지의 회차별 상영 시간을 갱신했다. 특별상영 도슨트도 9편으로 맞추고 바뀐 작품 길이를 관련 가이드에 반영했다.

공식 작품 페이지가 `Schedule` 영역과 영화제 수상·초청 배지를 새로 표시하면서 소개문에 일정이 섞이고 배지가 장르 검색어로 들어갈 수 있는 수집기 문제를 수정했다. 수집기는 소개문 경계를 구분하고 배지와 장르를 분리한다. 작품·상영표·도슨트 검증은 새 공식 수량과 공지의 주요 변경값을 확인한다. 변경된 `screenings.json`의 내용 해시가 다음 빌드의 데이터 버전이 되므로 이전 브라우저 캐시와 구분된다.

`npm run validate:films`, `validate:data`, `validate:curator`, `validate:curator-media`, `npm run build`와 `git diff --check`가 통과했다. 새 《그래비티》 회차를 영화 검색에서 찾아 시간표에 추가하는 검사를 포함해 도슨트·장르·시간표 Chromium·iPhone WebKit 집중 E2E **66건**이 통과했다. `541ad72`의 원격 전체 검증과 Pages 배포·공개 사이트 검증도 성공했고, 공개 작품·상영표 파일이 커밋본과 같은 해시임을 확인했다.

## 14차 구현: 작품·상영표 동시 갱신과 수집 결과 안정화

기존 수동 수집 워크플로는 작품 상세만 갱신해 상영표가 다른 시점에 머무를 수 있었다. 이제 한 번의 실행에서 공식 작품 상세와 날짜별 상영표를 차례로 만들고, 작품·상영표·도슨트·사진 메타데이터 검증이 모두 통과한 경우에만 두 데이터 파일과 메타데이터를 함께 커밋한다. 변경이 없으면 메타데이터의 수집 시각만 바뀐 커밋을 만들지 않는다. PR과 데이터 브랜치 자동 실행은 수집기·공식 데이터·워크플로 파일 변경으로 한정했다. 자동 예약 실행은 추가하지 않았으며 수동 실행과 데이터 브랜치 갱신 경로를 유지한다.

공식 작품 페이지의 `MORE` 관련 작품 추천은 요청마다 달라졌다. 재수집만 해도 246편의 원문 해시·사진 목록이 바뀌던 원인이어서, 고정 작품 사진과 소개·제작 정보를 남기고 변동 추천은 정적 데이터베이스에서 제외했다. 같은 공식 페이지 247편을 연속 두 번 수집한 결과 `films-2026.json`의 바이트와 SHA-256이 일치했다. 실제 작품 사진 URL 1,053개는 전부 유지됐고, 새 작품 데이터로 만든 273개 항목·752회차 상영표는 기존 커밋의 내용과 일치했다. 수집 파일의 줄바꿈과 메타데이터 경로도 운영체제에 관계없이 일정하게 기록한다.

## 15차 구현: 예매 계획과 대안 적용 화면의 가독성

예매 계획·충돌·대안 적용 화면의 일부 글자가 8~10px이고 요약·닫기·행동 버튼이 30~34px인 상태를 확인했다. 회차 보조 정보에는 실제 DOM 계층과 맞지 않는 선택자도 있었다. 정보 글자를 최소 12px로 조정하고 실제 요소에 스타일을 적용했으며, 주요 버튼의 높이를 44px 이상으로 높였다. 긴 작품명과 회차 정보는 카드 안에서 줄바꿈되도록 했다. 밝은·어두운 화면의 카드와 상태 영역에는 공통 색 토큰을 적용했다.

적용 확인창의 투명한 유리 배경 뒤로 시간표 글자가 겹쳐 보이는 문제도 iPhone WebKit 화면에서 확인했다. 예매 충돌창과 대안 적용창의 배경 불투명도를 높여 결정 문구가 분리되어 보이게 했다. `npm run build`와 예매 대안 적용·충돌·우선순위·모달 초점 검사 Chromium·iPhone WebKit **35건**이 통과했다. 새 검사는 회차 글자와 버튼 높이, 대화상자 배경 불투명도, 가로 넘침을 확인한다. 화면 증거: [예매 계획 밝은 화면](playwright/booking-plan-light-webkit-iphone.png), [예매 계획 어두운 화면](playwright/booking-plan-dark-webkit-iphone.png), [적용 확인 밝은 화면](playwright/booking-apply-light-webkit-iphone.png), [적용 확인 어두운 화면](playwright/booking-apply-dark-webkit-iphone.png).

원격 전체 검사에서 WebKit 연속 대안 전환 흐름이 실패해 Linux Playwright 1.63.0 환경에서 재현했다. 입력 기록상 적용 버튼을 누른 좌표는 버튼 안이었지만, 기본 마우스 초점 이동이 페이지를 23px 스크롤해 놓는 순간의 대상이 카드 배경으로 바뀌었다. 예매 계획의 적용·해제 버튼은 왼쪽 마우스를 누를 때 기본 초점 스크롤을 막고 기존 클릭 동작을 실행한다. 키보드 초점과 Enter 동작은 유지한다. 수정 뒤 클릭 전후 좌표가 유지되고 확인창이 열리는 것을 추적 기록으로 확인했다. 상세창 제거·초점 복귀를 기다리는 검사와 긴 연속 여정의 실행 시간 여유도 적용했다. 터치 입력·창 닫기·호출 버튼 초점 복귀·Enter 재실행을 포함한 Linux Chromium·iPhone WebKit 관련 검사 **35건**이 통과했다.

## 이어서 구현·확인할 범위

- 9월 29일 공식 변경분은 앱 일정과 행사 카드에 반영했다. 수동 수집 워크플로는 작품·상영표를 함께 갱신하지만 이후 공식 변경의 자동 예약 동기화는 하지 않는다. 작품 수나 도슨트 근거가 바뀌면 검증을 통과하도록 직접 내용을 확인·수정해야 한다.
- 공식 사진 URL과 출처 표기는 재사용 허가의 증거가 아니다. 권리 확인과 실제 이동통신망에서의 사진 로드 측정이 남아 있다. 외부 사진은 앱 서비스 워커에 캐시하지 않으며 현재 슬라이드만 지연 로드한다.
- iPhone WebKit 자동화에서 네트워크 차단 후 페이지 재열기는 WebKit 내부 오류로 검사하지 못했다. 기존 데이터 캐시·요청 실패 WebKit 테스트는 통과했지만, 설치된 iPhone PWA의 완전 오프라인 재진입은 실기기 확인이 필요하다.
- 네 탭의 공통 셸과 시간표 목록·그리드·빈 상태·영화 상세·설정의 주요 정보 위계, 데스크톱 밀집 날짜 집중 보기는 정리했다. 화면 내부의 레거시 CSS 전체를 새 디자인 체계로 교체하지 않았고, 설치형 PWA의 실기기 동작은 확인해야 한다.
